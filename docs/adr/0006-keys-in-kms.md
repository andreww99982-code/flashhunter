# ADR 0006: Приватные ключи — только KMS/HSM, не в git и не в Secret

**Дата:** 2026-09-28 · **Статус:** принято

## Контекст

Keeper-кошелёк подписывает транзакции, которые двигают реальные деньги. Его
компрометация = мгновенная потеря всего баланса. Стандартная практика «положить
ключ в .env / в Kubernetes Secret» оставляет несколько путей утечки: файл в
бэкапе, значение в логе `docker inspect`, чтение Secret из пода с другой ролью,
случайный `git add .env`.

## Варианты

1. **`.env` на диске.** Просто; ключ в открытом виде в файловой системе.
2. **Kubernetes Secret.** Чуть лучше, но значение доступно любому поду с правом
   чтения Secret, и его видно в `kubectl get secret -o yaml` (base64 ≠ шифрование).
3. **Внешний KMS/HSM + инжект при деплое, права 0400, аудит доступа.** (выбрано)
4. **Аппаратный HSM с подписью по сети (AWS KMS sign / YubiHSM).** Максимальная
   защита, но добавляет сетевой вызов в горячий путь (~10–40 мс) — выходит за
   бюджет 5 мс в момент отправки bundle.

## Решение

* Приватные ключи **не хранятся в репозитории ни в каком виде** (`.gitignore`
  закрывает `.env`, `*.key`, `secrets/`, `keystore/`).
* В продакшне ключ лежит в AWS Secrets Manager под KMS-ключом с ротацией;
  Ansible выгружает его на ноду в файл с правами `0400`, владелец — пользователь
  бота; доступ к файлу пишется в auditd (`-w .../secrets -p rwa -k flashhunter_keys`).
* Kubernetes: ключ монтируется через `secrets-store-csi-driver` из внешнего
  хранилища в эфемерный том (`flashhunter-keys`); в манифестах только имя класса.
* **Средний путь для масштабирования:** on-chain лимиты + малый баланс keeper-а
  (горячий кошелёк держит только необходимое на день, остальное — на холодном
  адресе, автосивип по расписанию). Даже при краже ключа потери ограничены.
* Проверка: `scripts/preflight.sh` блокирует старт в live-режиме, если в репозитории
  найден файл, похожий на приватный ключ.

## Последствия

**Плюсы:** утечка ключа требует компрометации облачного аккаунта, а не чтения
репозитория или пода; аудит доступа к ключам обязателен; ущерб ограничен балансом
горячего кошелька.

**Минусы:**
* деплой сложнее: нужен доступ к KMS и права instance profile;
* ротация ключей требует процедуры (перенос баланса, обновление адреса в контракте
  через `setKeeper`);
* путь к ключу (`KEEPER_KEY_PATH`) придётся учесть при локальной разработке:
  в dev-режиме используется keystore Anvil с фейковыми средствами.
