# ADR 0002: SQLite по умолчанию, Postgres + ClickHouse в проде

**Дата:** 2026-09-16 · **Статус:** принято

## Контекст

Требование ТЗ: «git clone && docker compose up -d → работает». Одновременно
проект должен жить в продакшне с потоком телеметрии (латентность каждого этапа,
отправки в релеи, тики PnL) и требованием не терять данные при отказе узла.

Поток записи оценивается так: ~2 блока/сек на 5 сетей → ~10 строк телеметрии
на блок → ~2 млн строк в сутки. Это уже не SQLite-нагрузка.

## Варианты

1. **Только SQLite.** Ноль зависимостей, но нет репликации, конкурентная запись
   блокирует чтение, аналитика на млн строк деградирует.
2. **Только Postgres.** Прод-качество, но запуск «из коробки» требует поднять
   СУБД, применить миграции, настроить пользователей — ломает простой старт.
3. **Только ClickHouse.** Идеален для телеметрии, плох для транзакционных данных
   (нет настоящих транзакций и уникальных ограничений).
4. **SQLite по умолчанию + Postgres для транзакций + ClickHouse для телеметрии.** (выбрано)

## Решение

* `FLASHHUNTER_DB_MODE=sqlite` (по умолчанию) — один файл в volume, схема
  создаётся моделями SQLAlchemy при старте. Это режим docker compose «из коробки».
* `FLASHHUNTER_DB_MODE=postgres` — прод: те же 17 таблиц, партиционирование
  `opportunities`/`trades` по месяцам, BRIN-индексы на журналах.
* ClickHouse — отдельная шина телеметрии: `latency`, `relay_submissions`,
  `pnl_ticks`, `service_health` + `MergeTree` с TTL 180/365 дней.
* Миграции лежат в `migrations/` и соответствуют моделям один-в-один.

## Последствия

**Плюсы:** запуск локально за одну команду; прод масштабируется по хранилищу
независимо от приложения; телеметрия не замедляет транзакционную базу.

**Минусы:**
* три SQL-диалекта в поддержке: нужен аккуратный CI-прогон схем;
* агрегаты для `/analytics` считаются по-разному: в SQLite — в Python,
  в Postgres — вьюхами (`v_pnl_daily`, `v_latency_by_service`);
* переход SQLite → Postgres не автоматический: нужен `scripts/migrate.sh`.
