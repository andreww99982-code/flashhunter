# Архитектура FlashHunter

Документ описывает, как устроен бот: слои, потоки данных, бюджеты времени,
точки отказа и то, как система сообщает о проблемах.

## 1. Слои

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 4. Наблюдение      UI (React 18) · Prometheus · Grafana · Telegram  │
├──────────────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 3. Управление      API FastAPI · RiskEngine · PnL · Backtest · Audit│
├──────────────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 2. Горячий путь    Стратегии · Симулятор · Bundle builder · Релеи   │
├──────────────────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 1. Данные          Ингестор · Индекс пулов · Граф токенов           │
└──────────────────────────────────────────────────────────────────────────────┘
              Контракты: FlashLoanArbitrage · Liquidator · JITVault · BridgeAdapter
```

* **Уровень 1 (данные).** Ингестор слушает новые блоки (WS) и события пулов,
  применяет их к индексу и держит снимок состояния: резервы, комиссии, тики.
  Индекс пулов отвечает на вопросы «сколько выйдет, если свопнуть X» за O(1).
* **Уровень 2 (решения).** Стратегии читают снимок и предлагают возможности;
  симулятор проверяет маршрут локально (revm), сборщик формирует калиброванную
  транзакцию, клиент релеев рассылает bundle во все релеи сети параллельно.
* **Уровень 3 (управление).** Риск-движок пропускает или блокирует каждую сделку
  и умеет остановить всё (kill-switch). Здесь же PnL-трекер, аудит всех действий
  оператора, API и движок бэктеста.
* **Уровень 4 (наблюдение).** Панель на 12 страниц, метрики Prometheus и алерты.

## 2. Горячий путь: от блока до bundle

```
 t=0.00 мс   RPC, WSS: eth_subscribe(newHeads) → новый блок
 t=0.02 мс   Ингестор: разбор заголовка, base_fee, timestamp              ← 5 мс бюджет
 t=0.50 мс   Индекс пулов: применение Swap/Sync событий, обновление снимка ← 2 мс
 t=1.20 мс   Граф токенов: поиск циклов (≤4 хопа), отсечение по комиссиям  ← 3 мс
 t=1.90 мс   Стратегии: отбор кандидатов (фильтры газа, размера, ROI)     ← 5 мс
 t=3.10 мс   Симулятор: локальный прогон маршрута, точный output и газ     ← 8 мс
 t=3.90 мс   Риск-движок: лимиты, экспозиция, свежесть данных             ← 1 мс
 t=4.30 мс   Bundle builder: calldata, nonce, maxFeePerGas                ← 3 мс
 t=5.00 мс   Подпись и fan-out по релеям (таймаут 250 мс на релей)        ← 10 мс
```

Бюджеты зафиксированы в `python/flashhunter/api/ws.py` (`SERVICE_BUDGETS_US`) и
проверяются метрикой `within_budget`: превышение бюджета — сигнал, что мы
проигрываем конкурентам, даже если сделки пока прибыльны.

## 3. Модель исполнения сделки

```
  Возможность найдена
        │
        ▼
  RiskEngine.check()  ── отказано ──▶ журнал + метрика, выход
        │ разрешено (reserve экспозиции)
        ▼
  Симуляция (revm/eth_call) ── реверт ──▶ record_outcome, выход
        │ успех
        ▼
  Сборка bundle (calldata + nonce + maxFee)
        │
        ▼
  Fan-out по релеям (параллельно, таймаут 250 мс)
        │
        ├─ принят хотя бы одним ─▶ ожидание включения в блок
        └─ не принят ни одним ──▶ replacement (тот же nonce, +15% комиссии)
                                      │
                                      └─ но и он не включён ─▶ cancel (self-transfer)
```

Атомарность сделки обеспечивает контракт: если после свопов прибыль меньше
`minProfit`, транзакция ревертится целиком, флеш-кредит возвращается, потери
ограничены сожжённым газом.

## 4. Контур риска

| Механизм | Триггер | Действие |
|----------|---------|----------|
| Дневной лимит убытка | PnL за сутки ниже `RISK_DAILY_LOSS_LIMIT_USD` | Отказ в новых сделках + kill-switch |
| Часовой лимит убытка | Убыток за час выше лимита | Пауза на 30 минут + алерт |
| Просадка | Equity-кривая ниже максимума на `X%` | Снижение размера позиций вдвое |
| Доля ревертов | > 35% сделок ревертятся за 10 минут | Отключение стратегии до разбора |
| Устаревшие данные | Снимок пула старше 5 с | Запрет сделок по этому пулу |
| Потеря соединения | Нет головы сети > 5 с | Отмена всех неотправленных bundle |
| Экспозиция | Превышен лимит на сеть/токен/кошелёк | Отказ и запись в аудит |
| Kill-switch | Автоматически или кнопкой оператора | Полная остановка отправки bundle |

## 5. Точки отказа и деградация

| Отказ | Поведение системы |
|-------|-------------------|
| Основной RPC упал | Переключение на резервный из пула; при отсутствии — пауза + алерт |
| Релеи недоступны | Bundle не отправляются, возможности копятся в журнале; после восстановления — запрет «догонять» старые блоки |
| Симулятор упал | Сделки не отправляются (fail-closed), алерт critical |
| Индекс пулов отстал | `stale` государства блокирует сделки по этим пулам |
| Упал API | Оркестратор продолжает работу (в кластере — лидер-лок), панель переподключается |
| Диск заполнен | Лог-ротация + автоочистка телеметрии (retention 90 дней) |
| Утечка keeper-ключа | Ущерб ограничен балансом горячего кошелька (автосивип), контракт переводится на новый keeper |

## 6. Наблюдаемость

* **Метрики** (`/metrics`): возможности, сделки по статусам, PnL, латентность
  по этапам, отправки и задержки релеев, газ, состояние предохранителей.
* **Алерты** (`infra/docker/alerts.yml`): падение API, остановка оркестратора,
  лимит убытка, превышение бюджета латентности, рост ревертов, просадка приёма
  bundle, «залипший» dry-run.
* **Журналы:** `audit_log` (кто что менял), `event_log` (события системы),
  `trades`/`opportunities` (что и почему было сделано).
* **Бэктест:** ночной CronJob гоняет 500 блоков и падает, если стратегии
  перестали быть прибыльными — регрессия ловится до реальных потерь.

## 7. Схема данных

```
networks ─┬─ tokens ─┬─ pools
          │          │
          └─ opportunities ── trades ── wallets
                                │        │
risk_limits ── kill-switch      │        └─ sweeps на холодный кошелёк
settings ── api_keys ── sessions │
audit_log · event_log · latency_metrics · backtest_runs · contracts
```

Подробности: `migrations/sqlite/001_init.sql` (локально) и
`migrations/postgres/001_init.sql` + `002_timescale_and_views.sql` (прод).

## 8. Что сознательно вне области

Сэндвич-атаки, эксплойты, атаки на других ботов, обход KYC/AML, обфускация.
Подробнее — `docs/adr/0005-no-sandwich-policy.md`.
